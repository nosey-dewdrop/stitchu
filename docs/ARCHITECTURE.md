# stitchu architecture

How a garment photo becomes a printable, body-fitted sewing pattern. The one companion doc that still exists is `engine/FORMULAS.md` (every drafting formula and its gotchas — the engine's spec). The two this line used to name alongside it — `PROJECT.md` (roadmap) and `PLAN.md` (track A/B directives) — **YOK**, neither does exist in this repo any more: `PLAN.md` was removed in `e8d66a3` and `PROJECT.md` in `94c475e` (the 29 Jul 2026 pivot to the 3D-surface line), and they were never replaced. Their live successors are `RULES.md` for the build discipline and `flatten-research/FINDINGS.md` for the milestone ladder; the deleted text is reachable only through `git show`. Corrected on 25 Aug 2026 rather than left pointing at nothing.

## The contract (`contract/`, K1 2026-07-19)

One versioned contract binds every layer boundary. `garment-spec.schema.json`: the SEMANTIC garment language (closed enums + bounded scalars) — the only language the vision model or a human speaks; the render layer is NOT in the contract, each renderer compiles its own parameters from the semantics, and the runtime gate (`web/js/spec-validate.js`, additionalProperties:false) strips any render knob smuggled into a vision answer. `tables.json`: every shared value (skirt lengths mm, EU size chart, gather ratios, flat drawing units, cross-layer word maps like sleeveHead→sleeveCap and the backDetail three-way split) — generated by `engine/tools/gen-contract.mjs` into `engine/src/contract.gen.hpp`, `web/js/contract.gen.js`, `backend/contract.gen.js`; consumers never copy numbers. `terms.json`: the term registry (id, canonical, synonyms, drawable|honest status, capability, evidence) — the benchmark counter's base since the DRAWN_SINCE regex list was retired. Guard: `engine/tools/validate-contract.mjs` runs as ctest `contract_check` and fails on any schema/vocab drift, registry defect, generated-file desync, 58-set unmapped phrase, undeclared flat recipe field, gate-fixture failure, or a create.js picker option outside the vocabulary.

## Layers

```
photo ──> Cloudflare Worker (Claude vision) ──> confirmed GarmentSpec
                                                      │
7 measurements (local) ───────────────────────────────┤
                                                      ▼
                        C++ engine (WASM, in-browser)
                        geometry core → blocks → garment drafter → validator
                                                      │
                                                      ▼
                        web app: SVG render → tiled A4 PDF print
```

### 1. Geometry core (`engine/src/geometry.*`)
Point/Path/cubic-Bezier primitives, seam-length measurement, outline offsetting, intersection and self-intersection checks. Everything above is built on these; they were unit-tested first (`tests/test_geometry.cpp`). Conventions (from `FORMULAS.md`): all geometry in millimeters, each piece in its own local space, curves flattened to 24 segments for length measurement (16 for self-intersection). Gotcha: `boundingBox()` counts curve control points, so comparisons must use flattened boxes.

### 2. Blocks (`bodice.cpp`, `skirt.cpp`, `sleeve.cpp`)
Parametric drafting blocks from published sources (FreeSewing Bella/Titan, Muller & Sohn, Aldrich), driven by 7 measurements plus percent ease (never fixed cm). Documented assumptions (underbust = bust − 70 mm, shoulder drop ≈ 13°) are flagged in `FORMULAS.md` and covered by the muslin warning in the sewing guide — an assumption is not a verified figure, and the three block quantities a publication does bind (scye depth, shoulder width, back-neck drop) are the ones `ctest -R draft_math_check` measures against Aldrich; the other assumptions are judged by nothing and are declared here for that reason (§13).

### 3. Garment drafter + manipulation layer (`garment.cpp`, `ruffle.cpp`, `keyhole.cpp`)
Combines blocks into garments (dress = bodice + skirt + CB invisible zipper; tops with hem variants) and applies the couture vocabulary: necklines (crew/scoop/v/square/boat/sweetheart), keyhole cut-out with shaped facing, halter (a frame-shift over the same bodice skeleton — no separate block), tiered ruffles (tier i edge = edge × fullness^(i−1)), pleats, gathers. Every vocabulary feature is an opt-in `GarmentSpec` field defaulting OFF. Read that as the invariant the per-feature `_check` tests and the golden pin ENFORCE — whether the base draft actually moved is what `ctest` and `golden_check` print, not something this line asserts (standing wording replaced 24 Aug 2026, RULES §6).

### 4. Seam allowance / cut line (`geometry.cpp offsetOutline`)
The piece outline IS the sewing line; the cut line is a drawn outward offset. The outward side is found empirically (probe the longest edge's normal with point-in-polygon — traversal direction is not trusted, an area-sign heuristic once shipped an inward offset). Per-edge offset with miter/bevel joins, then an envelope guarantee: relax passes push any point closer than the allowance back out to exactly it (tames concave curves with radius < allowance, e.g. sleeve underarm). Fold edges are not seams: clamped, exempt from the audit. Strip pieces (ruffles, bias binding) stay single-line — their allowance lives in the cut note.

### 5. Validator (`validator.cpp`)
Geometric invariants run on every draft, and at runtime before any PDF: side-seam balance, dart sums, armhole/cap ease, waist joins, self-intersection, print fit, cut-line sanity. A broken pattern cannot reach the printer. Trim pieces (names containing "Ruffle") are excluded from structural sums by design.

⚠ **Read "armhole/cap ease" through §15 (25 Aug 2026, V7).** Until that phase the validator found the sleeve by a substring of the piece NAME, took the cap by a hard-coded `commands[0..2]` index and compared it against a scalar copy of the armhole length rather than against the drawn armhole. It now addresses both edges by ROLE and measures both arcs off the drawn commands; the instrument that prints the numbers is `node engine/tests/sleeve_cap_ease_check.mjs`, and where no piece carries an armhole role the validator still falls back to the scalar and the gate counts that fallback by spec name (§15).

### 7. WASM boundary (`engine/wasm/bindings.cpp`)
A thin embind layer exposing `draftJSON(measurements, spec) → JSON pieces`. Built by `engine/build-wasm.sh` into a single-file bundle (`engine/dist/stitchu-engine.js`), copied to `web/vendor/`. `ls -l engine/dist/stitchu-engine.js` is what prints its size; the reading moves with every rebuild, so it is dated here rather than asserted: 1 209 765 bytes on 24 Aug 2026 (`GECE/V0.md` §1.4), and **1 253 817 bytes on 25 Aug 2026** (same command, artefact timestamped 09:17) — +44 052 bytes in one day. Both readings are recorded because the drift is the point: the "~218 KB" figure this line originally carried was stale by roughly 5.5× and was corrected, not deleted. Run the command for today's number; the artefact is gitignored, so a clean checkout has none. The same file is `require()`-able from Node, which is how the fuzz/precision/proof tools drive the real engine — no parallel JS implementation to drift.

**The boundary refuses; it does not coerce (24 Aug 2026, V2-C).** Until this phase the conversion layer was the quiet failure point, and both defects were measured on the shipped byte before anything was changed (`GECE/V2-C.md`, log `GECE/log/V2-C.bostest.txt`):

- *Int enums.* `intField()` went through `v.as<int>()`, so truncation happened INSIDE the JS→C++ conversion and `parseEnumInt` never saw the real value — a spec asking for `sleeveCap 1.5` drafted as `1`. All 26 int axes now read through one `enumIntField()`: a non-integral, non-finite or out-of-range value is refused BY NAME, in the same `specparse.hpp vocabError` words the string axes already use (`invalid sleeveCap '1.5' (valid: plain, gathered, puffed, …)`). Absence is still not an error — an undefined key keeps the default. `ruffleTiers` is a count rather than an axis and was going through the same truncation; it is bound to the strict reader too.
- *Body fields.* `numField()` turned a key it could not find into `0`, and a missing measurement is not a zero measurement. `bodyFrom()` now names the offending measurement in the recipe interpreter's own words (`recipe.cpp:938`, one fault one language); `upperBust` stays optional (0 = not declared). The zero body was also what produced the `collarType` NaN — the real root was a missing `shoulderLen < 1e-6` latch in `bodice.cpp makeFacing()`, and `num()` printing a bare `nan` token made the validator's honest verdict unreadable as JSON. `num()` now refuses to print a non-finite number and the throw is caught into `{"error": …}`, so the failure is noisy instead of hidden. `gradeJSON`, `draftRecipeJSON` and `dxfRecipeJSON` carry whole-body try/catch for the same reason.

**The shipped artefacts carry a source digest (24 Aug 2026, V2-D).** `build-wasm.sh` prepends a line-1 comment to both glue files and appends a `stitchu.source-stamp` custom section (wasm id 0, spec-legal, ignored by every runtime) to `backend/engine/stitchu-worker.wasm`, all three carrying a sha256 of `engine/src` + `engine/wasm` + `build-wasm.sh`. The reason it is a digest rather than the producing commit sha is written in the script: a sha is only right if the build runs after the source commit, and the normal order (edit → compile → one commit) builds from a dirty tree, so a sha stamp would re-emit the same value and leave `bundle_fresh_check` red — the very defect being repaired. A digest is also deterministic, so a rebuild with no source change produces no diff. Two limits are declared rather than glossed (`GECE/V2-D.md` §6): `engine/dist/` is gitignored and unstamped, and the gate reads the stamp as an assertion instead of recomputing it from content.

### 11. Where does the flat's outer contour come from? (24 Aug 2026, V3)

Until this phase the flat and the pattern were two unrelated drawings of the same garment. The flat came from a 2D croquis (`contract/flat-convention-v1.json` → `engine/tools/render-garment-flat.mjs`, with a second reference pen in `engine/flat-engine/_engine-full.mjs` that draws 31 styles off its own croquis); the pattern came from the 3D `GarmentSurf` shell inside `engine/src/surfacepattern.cpp`. ⚠ Read that last clause as *the native pattern*: on 25 Aug 2026 the shipped download path was walked and it does not go through `surfacepattern.cpp` at all (§13, opening paragraph). They shared one thing — the EU size chart row in `contract/tables.json` — and neither called the other. That inventory, with the file:line for each claim, is `GECE/V3-K.md` §3.

**A second flat line now exists, and it is computed rather than drawn.** `GarmentSurf` — the same shell the pattern is cut from — was published from the anonymous namespace of `surfacepattern.cpp` into `engine/src/surfacepattern.hpp`; every definition stayed where it was and no second shell class was written (that duplication is the exact error the single-waist-ring law exists to kill). Its configuration — ease, skim envelope, hem sweep, hip blend — was lifted out of `buildSheathPattern` into one `buildGarmentSurf(body, opt)`, so both consumers configure the shell in one place. `engine/src/shellprojection.{hpp,cpp}` then projects that shell orthographically. The single claim is declared at the top of the file: under a −y orthographic projection the silhouette of a convex section is its extreme x, which on the offset section is the phi=0 point where the normal is horizontal, and there the offset point is exactly `(a + d, 0)` — so the silhouette half-width is `a + d`. No fitted algorithm, no coefficient. The tool is `engine/build/shell-flat EU38`: JSON with six measures, front/back outline points, the ring span each point belongs to and the fitted cubics; `--svg` emits a 1:1 SVG carrying `data-scale="1"`, `data-source="GarmentSurf"`, `data-size`.

**The old drawing line was NOT deleted.** `engine/tools/render-garment-flat.mjs`, `engine/flat-engine/` and `web/` were not touched. The two lines run side by side and disagree by construction: the croquis is a zero-ease body line, the shell carries garment ease. Which one the site ships is not decided here.

The pattern side got its own ruler so the two can be compared at all. `node engine/tools/pattern-measure.mjs <pattern.json>` reads the same six measures off the drafted panels — arc-length integration of the spec's own cubics — and where the pattern has no such edge it returns `null` **with a written reason** instead of deriving a number from a neighbouring one. Three of the six come back null today and they share one root: `surface-pattern` drafts a STRAPLESS garment, so there is no bust edge, no neckline and no shoulder in the stitch graph (`GECE/V3-B.md`). That is the open G5 work, seen from the measurement side.

**Two gates were added, and both are red today (`engine/tests/`).** They were built to be red; neither was relaxed to pass. Empty-test proof for both is `GECE/log/V3-C.vacuous.txt` (the pre-phase flat artefact, judged by the same instruments, fires all four artefact classes and all six agreement rows), mutation evidence `GECE/log/V3-C.mutation.txt`.

- `flat_pattern_agree_check` — compares the six measures, tolerance 1.5%, and the test's own header states that the 1.5% is a DECISION, not a published figure: no standard was found that binds a technical flat numerically to a pattern (`GECE/V3-R.md` EŞİK 2). It also ratchets the UNMEASURED count at 3, so that number may fall and may not rise. What it printed on 24 Aug 2026: 1 violation — `body_length` flat 757.5584 mm vs pattern 728.7870 mm, −3.7979%. An earlier −1.98% reading was an apples-to-oranges artefact and was repaired first: the shell now integrates its own centre-front arc at the same 0.05 mm step the pattern ruler uses, instead of reporting a vertical height difference. The vertical figure was not deleted — it is reported beside the table as `body_height_projected` and the gate compares it to nothing. The remaining gap is the G5 hole (the shell's arc starts at the shoulder ring, the pattern's at a strapless free top edge) and it was **not decomposed** (`GECE/V3-D.md` §3).
- `flat_artifact_census` — counts four artefact classes on the shell contour (jagged edge, self-intersection, C1/tangency discontinuity, degenerate segment / non-positive area), each with its published name where one exists and its source file:line where one does not. The C1 threshold is 1.0°, sourced to the McNeel Rhino document angle tolerance default; the stricter CATIA V5 GSD 0.5° precedent is recorded next to it and deliberately NOT wired to the gate (confidence medium, page 403). What it printed on 24 Aug 2026: 1 violation — class 3, 2 points at 20.560216°, at the waist, front and back. Classes 1, 2 and 4 print 0; the raw sign-change count (246) is printed too rather than filtered away.

**One repair landed, one was measured and reverted.** Degenerate segments went 6 → 0 by writing each run boundary to the outline once instead of twice — no point moved, no fit changed, the closed-contour area read 2451.09 cm² before and after (`GECE/log/V3-D.census.{before,after1}.txt`). The waist C1 break was attacked with the mechanism that already solves the same corner at the hip (the `blendMM` quadratic corner round in `surfacepattern.cpp`); it closed the break to 0.458177° and pushed the waist ring +36.1166 mm, which turned `surface_pattern_check`, `edgemono_check`, `walkgate_check` and `cutplan_check` red — so it was **reverted, and the 1.0° threshold was not touched** (`GECE/log/V3-D.waistblend.rejected.txt`). A Bézier does not pass through its control point and the waist is a local minimum of half-width, so rounding that corner adds cloth there; any future fix has to hold the waist ring at its measured value. Two candidates are written down in `GECE/V3-D.md` §2 and neither has been measured.

Run them:

```
./engine/build/shell-flat EU38                      # JSON, six measures + contour
./engine/build/shell-flat EU38 --svg                # 1:1 SVG
./engine/build/surface-pattern EU38 > /tmp/p.json
node engine/tools/pattern-measure.mjs /tmp/p.json   # pattern side, nulls with reasons
node engine/tests/flat_pattern_agree_check.mjs
node engine/tests/flat_artifact_census.mjs
```

Declared limits of this line, so they are not read as absent: only EU38 was measured, the other seven sizes were not looked at; the contour starts at the SHOULDER ring and carries no sleeve, armhole or neckline, so what `shell-flat` prints is a silhouette outline, not a technical flat; front and back come out identical because an orthographic projection of one convex shell does, and the real front/back difference is interior; the closed contour class 2 is judged on a mirror of the half chain, because the engine does not emit a closed contour object.

### 12. Does the drawn flat obey a convention, and does it draw what the spec asked for? (24 Aug 2026, V4)

§11 is about the *computed* contour. This section is about the other line — the **drawn** flat, `engine/tools/render-garment-flat.mjs` under the law in `contract/flat-convention-v1.json`, judged by `engine/tests/flat_convention_check.mjs`. Both lines were measured side by side first (`GECE/V4-K.md`): the computed shell accepts 8 sizes and **0** style parameters, declares 0 of the law's 5 line classes, and draws 0 of the 9 technical-drawing elements (shoulder seam, armhole, collar, sleeve, dart, panel seam, topstitch, closure, hem); the drawn pen accepts one size and ≥22 style values and draws 9 of 9. That measurement is why the convention gate judges the drawn pen and takes the shell in as a report line rather than as a defendant.

**A gate was assuming the very flaw it existed to fix, and that was repaired at the root.** The gate inferred the shoulder tip as "the first local maximum of x walking down from the centre-front neck" — an intuition that is only correct when the shoulder is *wider* than the chest. `measureCroquis` now finds the shoulder tip as the corner where the shallow, outward-going shoulder chord meets the steeply descending armhole chord, which asks nothing about the shoulder/chest ratio; the criterion reads only the drawn polygon's chords, no `data-*` declaration and no law number (the anti-hack property was kept). The same inference was run against both croquis — shoulder outside the bust and shoulder inside it — and found the right corner in both (`GECE/log/V4-A.inference.txt`).

**With the inference fixed, a measured correction that had been blocked for a day was applied.** `croquis.landmarks.shoulderTipX` went 78.0u → **70.1799u** and the derived `shoulderTipY` 19.36u → **16.8576u**. The size comes from the purchased Buğra Locket EU38 `Back Body` piece — shoulder/chest half-width 196.13/204.94 = 0.9570 — but the *condition* the new gate line (1c) enforces is a geometric law, not a resemblance: in a set-in-sleeve garment the armhole shares its endpoints with the shoulder tip and the underarm, so the shoulder tip cannot sit outside the chest line. There is no threshold in that gate line, only an inequality. The old values were not deleted; `_previous`, the earlier `_F_E_OLCULDU_AMA_DEGISTIRILMEDI` note and the reason the change was blocked all stay in the contract next to the new number. `render-garment-flat.mjs` was not edited — it reads the law, so the drawn shoulder moved on its own, and a search for a hand-written copy of the old number came back empty.

**A second gate was added because the pen was silently collapsing different garments into the same drawing.** `flat_expresses_spec_check` (registered in `engine/CMakeLists.txt`) was measured on 24 Aug 2026 and it printed the collapse: `sleeveStyle` set / raglan / puff came back **byte-identical** as SVGs, as did `collarType` 1 / 2 / 3 — the exact failure class `CLAUDE.md` already records for 2026-07-18 ("sleeveStyle 'puff' silently dropped"). That is a dated reading of a DEFECT, not a standing property; evidence `GECE/V4-B.md`, and `ctest -R flat_expresses_spec_check` is what prints today's. The gate's unit of difference is geometry (the set of drawing elements plus contour length), not a hash, and its verdict is equality/inequality, so there is no threshold to relax. ### 15. Does an edge have a NAME, and is the sleeve judged against a drawn armhole or against a copy of one? (25 Aug 2026, V7)

§14 ends on "the artefact carries 0 named edges". This section is what changed underneath that sentence, and what did not.

**The defect was a tautology, and it was measured before it was touched (`GECE/V7-A.md`).** `PatternPiece` carried a name for the PIECE and for nothing else, so every consumer that needed "the armhole" or "the cap" had to guess it back three ways at once: the sleeve was found by the substring `"Sleeve"` in the piece name (`validator.cpp:280-286`), the cap edge by a hard-coded `commands[0..2]` layout (`:289-295`), and the armhole was not read off geometry at all but off a scalar, `bodice.armholeLength`, written at `bodice.cpp:509`. `sleeve.cpp:46-96` then SOLVED the cap by bisection against that same scalar. So the armhole↔cap agreement the validator reported was one number agreeing with itself; it could not be wrong out loud.

**An edge role is a NAME given by the code that DRAWS the edge, and it addresses the edge instead of summarising it (`engine/src/geometry.hpp:40-71`, `GECE/V7-C.md`).** `struct EdgeRole` carries `role` + an inclusive `firstCommand..lastCommand` index range into `PatternPiece::commands` + `start`/`end` endpoint anchors. There is deliberately **no length field**: a copied scalar is the exact failure being replaced, so the consumer rebuilds the edge and integrates its own arc length. Four roles exist today — `armhole_front`, `armhole_back`, `sleeve_cap`, `sleeve_underarm` — and they are emitted where the curve is pushed, not inferred afterwards: `bodice.cpp` names the armhole at the point it pushes `armholeCurve` (and names BOTH halves in the princess split, since the armhole is genuinely cut in two), `sleeve.cpp` names the cap and the two underarm side edges (both, because the underarm seam is those two edges sewn to each other and naming one would hide the pair). Where an edge does not exist it is not invented: a cap sleeve has no underarm seam and gets no `sleeve_underarm`, and the `Lower Sleeve` top edge of the two-piece Locket sleeve is a band seam rather than an armhole and was left unnamed on purpose. The role crosses the WASM boundary as `"edgeRoles":[{role,first,last,startX,startY,endX,endY}]` (`engine/wasm/bindings.cpp:283-301`), so it is on the artefact the buyer's browser drafts.

**The anchors are an integrity device, and they had to be, because the staleness they guard against was live in main.** `edgePathOf()` (`geometry.cpp:190-231`) returns EMPTY if the index range overflows *or* if the endpoints no longer sit where the drawing code left them — refuse, never coerce. `reanchorEdgeRoles()` (`geometry.cpp:233-262`) re-addresses a role from its own endpoints after a post-pass and **drops the name** when the anchor is gone, because a name pointing at the wrong edge is worse than no name; `garment.cpp:1077-1085` is the single choke point where that runs, after every post-pass and before any consumer reads. V7-C had written this hole down as theoretical. It was not: `locket.cpp rebuildFront()` rewrites the whole front outline and was staling `armhole_front`, and once that was closed four more gates (`cup_check`, `yoke_check`, `boxpleat_check`, `compose_check`) fell with the same message — every pass that rewrites a bodice outline was doing it (`GECE/V7-D.md` §7).

**The gate: `sleeve_cap_ease_check` (`engine/tests/sleeve_cap_ease_check.mjs`, registered in `engine/CMakeLists.txt:143-151`).** It loads `web/vendor/stitchu-engine.js` — the SHIPPED bundle — calls `draftJSON`, and measures the armhole arc (`armhole_front` + `armhole_back`, summed across every piece carrying them) against the cap arc (`sleeve_cap`), both integrated off the artefact's own `commands[first..last]`. No length is borrowed from the engine. Because it drives the shipped bundle, a native-green/wasm-broken split is red here without a separate parity test. Its thresholds are sourced in the file header rather than chosen: the ceiling is Linda Lee's published 1½ in = **38.1 mm** (`GECE/V7-R.md` §1.1 A1, the only cap-ease figure verified from its primary page this phase), the sign condition (cap ≥ armhole) comes from the engine's own `fabricease.hpp kCap` never going negative, the LOWER end of the band is printed as REPORTED and judged by nothing because no published formula scaling cap ease to the body was found (`GECE/V7-R.md` §3), and the ceiling is deliberately NOT applied to gathered/puff heads — that is scope, not relaxation, since a gathered head is not eased in, and no publication gives a quantitative definition of "puff" at all (§1.3). Unlike the §13 gates it carries **no ratchet and no ceiling file** — its exit code is bound to the thresholds themselves, so run it for today's verdict. Empty-test proof is `GECE/log/V7-D.bostest.txt` (the same tool pointed at the pre-phase artefact fires on all 48 rows); mutation evidence, including the one that grows a role stale, is `GECE/log/V7-D.mutasyon.txt`. The golden dump is untouched by construction — it reads `commands` + `markings`, and `edgeRoles` is metadata, same discipline as `notches`.

**The debt this created is printed by the gate itself rather than hidden.** Where NO piece carries an armhole role, `validator.cpp:333-352` still falls back to the old scalar, and the reason is written there: a missing name is a debt in the PRODUCER, not a defect in that draft, so refusing would stamp "unsewable" on correctly drawn patterns. ## Data flow summary

- Measurements: entered once, IndexedDB/local only, never leave the device for drafting.
- Photo: leaves the device only for the vision call (Worker → Anthropic), user confirms the classification before drafting.
- Drafting: 100% client-side (WASM) — zero server cost per draft, and simultaneously the KVKK/privacy answer.
- Pattern: SVG + PDF generated in the browser; saved patterns live in the local closet (full CRUD).
- Knowledge: `knowledge/schema.sql` + seeds → `stitchu.db`; formula claims enter as `verified` only after adversarial source-checking, refuted claims kept so they are never reused.

## Key design decisions

- C++ core, multiple consumers: one engine feeds web (WASM), Node tooling (same bundle), later iOS (static lib) and Android (NDK). Chosen over Rust deliberately (synergy with coursework); the golden matrix is what made a full Swift→C++ rewrite safe.
- Client-side drafting: no server cost, no measurement upload, shareable static hosting.
- Spec-driven port: `FORMULAS.md` is the source of truth, not line-by-line translation — the port implements the spec.
- Opt-in vocabulary: every new feature defaults off, and the draft matrix plus the base-draft golden pin are the gates that decide whether it stayed clean. Their verdict is read from their own output (`ctest`, `golden_check`), never asserted here — the standing-claim wording this line used to carry was replaced on 24 Aug 2026 under RULES §6, after `golden_check` was measured red (`GECE/V0.md` §1.2). That red was later traced to a deliberate behaviour change and answered with a declared re-pin (`engine/GOLDEN-PIN.md`, 2026-08-24, Damla approval still open) — which is why the gate's verdict is read from the runner and the ledger, and is not restated as a fact here.
- Prove, don't claim: a feature exists only when it is in `engine/src`, has a passing `_check` test, renders correctly, and survives the matrix + golden + precision + fuzz loop. That discipline used to be cited here as living in `PLAN.md`, which **YOK** — the file left the repo in `e8d66a3`. Its live home is `RULES.md`, "Per-feature discipline (all 7 steps, in order)", which is the wording to read; corrected 25 Aug 2026.
- One truth, one place: neck width, armhole curve, binding length each have a single computing site; derived values are measured from the same geometry, never recomputed.
