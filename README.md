# stitchu

**A deterministic FIXED-SIZE (EU34-48) pattern engine.** Give it a body and a garment, and it does not draw a pattern: it builds the garment as a 3D surface on that body and then flattens it. The darts are not formulas — they are the surface's own develop-deficit, opened where the flattening says it has to open. Same body, same garment, same millimetres, byte for byte.

That is the sealed architecture (28 Jul), and it is sealed because the alternative was tried first and found to be the wrong abstraction: a 2D formula draft treats the flat pattern as the primitive, when a flat pattern is an OUTPUT — what a 3D surface becomes when you flatten it.

> ⚠ **That paragraph is a sealed DECISION, and on 25 Aug 2026 it was measured against what actually ships — they are not the same thing.** The pattern a visitor downloads from `web/` is not cut by the surface line. The chain was walked file by file and ends at the older 2D block drafter: `web/js/create.js:730` → `web/js/engine.js:187 engine.draftJSON(...)` → `engine/wasm/bindings.cpp:339` → `:298 GarmentDrafter::draft(spec, m)` → `engine/src/garment.cpp`. The tool that settles it is the WASM source list, and it was re-run on 25 Aug 2026 rather than quoted: `grep -c "surfacepattern\|flatten.cpp\|curvefit\|bodysurface\|garmentshell\|shellprojection" engine/build-wasm.sh` printed **0**, against `grep -c "garment.cpp" engine/build-wasm.sh` = **2**, while the same six files are compiled into the native library (`engine/CMakeLists.txt:12-17`). The same run enumerated the build's whole source list — `grep -o '[a-zA-Z0-9_/.-]*\.cpp' engine/build-wasm.sh | sort -u` gives 36 unique files, 35 under `engine/src/` plus `engine/wasm/bindings.cpp`, and not one of the six is among them. So `surfacepattern.cpp` and `flatten.cpp` run in `ctest` (`surface_pattern_check`, `flatten_check`, `walkgate_check`) and reach no buyer. Read the sections below with that split in mind: the surface line is where this repo is going, the 2D line is what is on the site today.

Not made-to-measure, and that is a decision with evidence behind it: ZOZO, unspun and Fayma all died on MTM and Lekala hit a quality ceiling, because a girth does not determine a shape — two bodies with the same bust can need different patterns. stitchu sells graded fixed sizes. The run is EU34-48 because that is exactly the range for which the body contract publishes a front/back split (contract/layers/shape-ratios.json); EU50 and EU52 have no published ratio and are not claimed. That decision took until 25 Aug 2026 to reach the website, which was still selling made-to-measure and a EU34–52 run; the wording was removed from the pages and from the generators that write them, and the size axis was then bound to the contract by a test rather than by discipline (`ctest -R landing_truth_check`, described below). One honest split goes with it: the eight sizes are what the graded run publishes, while a single draft made in the browser still goes to the seven measurements the visitor typed (`web/js/create.js:730` → `web/js/engine.js:183`, walked 25 Aug 2026, `docs/ARCHITECTURE.md` §8).

The moat is not a chat box. Take the AI away and what remains is a real CAD: a recipe model, a deterministic geometry kernel, and an industry-standard interchange path. Below is what that kernel can already do, each capability proven by running it — not asserted.

## What can it already export to the factory floor?

The engine drafts to a recipe, then carries that geometry all the way to production-grade artefacts. Every item below was independently re-derived from a clean build against standard third-party tools (`ezdxf`, `shapely`, `poppler`); the machine-checked proof is in [`reports/gate/endustri-2026-07-28.txt`](reports/gate/endustri-2026-07-28.txt).

- **Industry interchange — DXF-AAMA/ASTM.** The kernel's own pattern-piece geometry exports to DXF R12 with `$INSUNITS=4` (mm) and the AAMA/ASTM layer convention (1 = boundary, 8 = seam, 7 = grainline, 11 = internal/dart, 4 = notch, 15 = text). Opened in `ezdxf 1.4.4`; the boundary was flattened through the *same* 24-step cubic-Bézier path as the kernel and compared vertex-for-vertex. The deviation and the vertex count are **whatever `ctest --test-dir engine/build -R dxf_check` prints** — the standing "max error 0.000e+00 mm across 50 vertices" wording was replaced on 24 Aug 2026 under RULES §6 (a frozen number is not a gate). The last dated reading of that comparison is in [`reports/gate/endustri-2026-07-28.txt`](reports/gate/endustri-2026-07-28.txt); the point of the test is that the DXF is the kernel's millimetres, not a drawing of them. (`engine/src/dxf.{hpp,cpp}`)
- **Size grading — one recipe re-drafted against each standard body.** The run this repo can publish ratios for is EU34–48: `contract/layers/shape-ratios.json` has no published front/back split at EU50 and aborts there, so the earlier "a full EU34–52 run / 10-of-10 sizes" wording contradicted the size run stated at the top of this file. It was corrected on 24 Aug 2026 (measurement in), not removed silently. What the graded run asserts — validator cleanliness, seam matching, monotonic growth, fixed dart topology — is whatever `ctest recipe_grade_check` prints when you run it. The point of that test is that growth is *not* a fixed step: it follows the EU chart's own +4 cm → +6 cm change, which is what separates grading a body from relabelling one pattern as a fake series.
- **Nesting / marker layout.** Cut pieces pack onto a fabric width and the overlap is checked by an independent geometry engine, not our own script. `shapely 2.1.2` computes the pairwise intersection area and the roll-width fit; the number it returns today is what `ctest -R nest_check` and the external `nest_marker_check` print, and the last dated reading (`reports/gate/endustri-2026-07-28.txt`) was 0.000000 mm². The frozen-number wording was replaced on 24 Aug 2026 under RULES §6. The detector is not blind — its smoke test sees a half-shifted overlapping copy and does *not* false-positive on far-apart copies. (`engine/src/nest.{hpp,cpp}`, ctest `nest_check` + external `nest_marker_check`)
- **Tech-pack — a machine-readable production package.** One recipe grades across the full size run into a single manifest (`stitchu.techpack/1`: size table + cut list + fabric weight + marker efficiency + a graded DXF per size) plus a human-readable PDF spec. The weight math (`metres × 1.40 × gsm`) and efficiency math (`area ÷ (width × roll)`) were cross-checked by hand to within rounding, and the manifest, the page count and the efficiency value are re-derived by `ctest -R tech_pack_check` plus the external `techpack-verify.py` — those two are what print the verdict. What makes the check a check rather than a rubber stamp is that a tampered efficiency value makes the verifier fail loudly; that is the mutation the tool carries, not a number this file states. (`engine/tools/tech-pack.cpp`)

## How is the pattern a document, not a picture? (the OLDER line)

> ⚠ **This section describes the 2D formula-draft line — and on 25 Aug 2026 that line
> was measured to be the one the buyer actually gets.** The sentence that used to sit
> here ("it is not where the dress comes from: the shippable garment is built by the
> surface line above") was **REFUTED**, not deleted: `engine/build-wasm.sh` compiles
> 35 `.cpp` files and `surfacepattern.cpp` / `flatten.cpp` are not among them, so the
> download path terminates in `GarmentDrafter::draft` (`engine/src/garment.cpp`).
> Two engines is still one too many and this is still the one that is meant to go —
> but until the surface line is in the WASM source list, *this* is the shipped engine
> and the sealed one is unshipped work.

The core architecture is a CAD model, not a pipeline. A pattern is a **recipe**: a formula-driven sequence of operations bound to a measurement table (Valentina file logic). The screen shows a rendering of the recipe; when a measurement changes, everything regenerates. SVG and PDF are only export formats.

1. **Recipe data model** — the pattern is a saved, editable construction document: named points, curves and dart operations whose coordinates are formulas over the measurement table, never stored numbers. Contract: the DSL's parser is its own spec — `engine/src/recipe.cpp` names every legal op and rejects unknown keys; a worked document is `recipes/shift-dress-square-spaghetti.json`. (The prose contract `docs/RECETE-SPEC.md` was moved out of this repo in `2f748db` and the link that used to sit here pointed at nothing; corrected 24 Aug 2026 rather than left dangling.)
2. **Deterministic kernel** — a C++ engine (compiled to WebAssembly, running entirely in the browser) is the single source of every number: geometry, seam-length equalisation, notches, grainlines. Zero guessing.
3. **Canvas** — a live drawing surface; change a measurement and the piece redraws. (Kapı 2, the taste gate, is judged by Damla — no claim made here.)
4. **Generative layer** — prompt/photo → *writes a recipe* (it never measures numbers or draws coordinates; it composes from the vocabulary). Take the LLM out and a complete CAD remains.

The recipe path re-derives a pinned golden subset through a *second* generation path rather than replaying the engine's own drafting calls — the verdict is whatever `recipe_golden_check` and `recipe_check` print. The independence is at the level of the construction document, not of the maths: where a curve is *solved* rather than stated, the recipe op names the frame and calls the kernel's own solver. The armhole is the case in point — the `scye` op (added 24 Aug 2026, `e4516cf`) hands `from`/`to`/`neck`/`innerX`/`maxInset` to `BodiceBlock::scyeCurve` instead of carrying copied control points, because the cubic is found by bisection against a measured arc and cannot be written down in JSON. One solver, two paths.

## Where's the rigour — what numbers back all this?

These numbers are the discipline, not a sales sheet. They exist so the product is actually correct, and they read as engineering rigour under the moat above — a boundary without a number does not exist.

- **Test suite — the count lives in the runner, not in this file.** `ctest --test-dir engine/build --output-on-failure` is the tool that prints how many tests are defined, how many actually ran, and which ones come back red. It was run twice independently on 24 Aug 2026 and the suite did **not** come back all-green. The older "77/77 green" wording was measured stale on that date and replaced rather than deleted quietly. The suite was run again the same day, before and after the V1 changes, and it still did not come back all-green. Run it yourself for today's red NAMES: the point of this bullet is that the count and the red set live in the runner's output, never in a sentence here (RULES §9).
- **Seam-pair precision — the worst pair is printed, not stated.** `node engine/tools/precision-report.js` measures every seam pair a tailor would actually pin, off the *drawn geometry* rather than the intended numbers, and fails above 1.0 mm. The standing "worst pair 0.00 mm" line was replaced on 24 Aug 2026 under RULES §6: run the tool for today's worst pair. (An earlier audit caught the benchmark reading intentions instead of geometry; it reads geometry now.)
- **DXF millimetre parity** over the boundary vertices, measured against a standard third-party parser (`ezdxf`) rather than our own exporter — see the DXF bullet above for which command prints the deviation.
- **The shipped WASM boundary refuses instead of coercing.** A fractional value on one of the 26 int-enum axes used to be truncated inside the JS→C++ conversion, so `sleeveCap 1.5` and `sleeveCap 1` produced the same bytes; a body whose measurement keys did not match was silently read as zeros and could reach the drafter. Both were measured on the shipped byte and both now come back as a named refusal in the engine's own words. `ctest -R wasm_spec_honesty_check` is what prints how many judgements ran and how many failed; is the same gate run against the pre-phase byte, which is how you can see it was ever red.
- **Determinism has a second face, and it now has its own gate.** "Same garment, same bytes" is only half the invariant; the other half is that a *different* garment must not produce the same bytes. It was measured doing exactly that on 24 Aug 2026: the flat pen drew byte-identical SVGs for `sleeveStyle` set, raglan and puff, and again for `collarType` 1, 2 and 3 — a silent collapse rather than a refusal, and the same failure class this repo already had on record from 2026-07-18. `ctest -R flat_expresses_spec_check` is what now prints how many spec values were separated and how many collapsed; its unit of difference is geometry (drawing elements plus contour length), not a hash, so its verdict is equality or inequality and there is no threshold in it to relax. Where the pattern engine genuinely cannot cut what the spec asked for, the flat stamps the missing operator's name onto the SVG root rather than drawing a substitute. The axes it still reports as collapsed are printed by the same run, not hidden.
- **The shipped bundle carries a digest of the sources it was built from.** `engine/build-wasm.sh` stamps `web/vendor/stitchu-engine.js`, `backend/engine/stitchu-worker.js` (a line-1 JS comment) and `backend/engine/stitchu-worker.wasm` (a spec-legal custom section, `stitchu.source-stamp`) with a sha256 of `engine/src` + `engine/wasm` + `build-wasm.sh`. A shipped artefact can therefore no longer be silently stale behind an engine change that happened to compile to the same bytes; `ctest -R bundle_fresh_check` prints the verdict. Its limits are written down rather than glossed: the stamp is an assertion the gate does not re-derive from content, and repo freshness is not liveness.
- **Golden reference pinned in the repo.** New capabilities are opt-in, and the pin exists so that a change cannot alter an old pattern unnoticed. Read that as the invariant the pin ENFORCES, not as a description of today's tree. On 24 Aug 2026 the pin did its job and reported drift — `ctest golden_check` came back red (records the drifting line count, the worst deviation and the single commit the drift was bisected to). Later the same day the drift was traced to a deliberate behaviour change (the scye depth was sourced to Aldrich p.11) and the reference was **re-pinned under declaration** in `engine/GOLDEN-PIN.md`, entry 2026-08-24: that entry carries the content diff, the independent `sloper_check` witness reading, and a refuted earlier claim left visible rather than deleted. That re-pin is **NOT taste-approved — it is waiting on Damla (K-V1A)**, so the new pin is a committed reference, not a closed decision. `./engine/build/golden_dump` and `ctest golden_check` are the tools that print the current answer.
- **Is the printed pattern actually sewable, and does its maths match a published block?** Two gates ask that of the *shipped* draft across 8 sizes and print every violation by name: `ctest -R sewability_check` (seam-pair equality, notch pairing, closed contours, corner turns, getting the garment onto a body) and `ctest -R draft_math_check` (scye depth, shoulder width, back-neck drop against Aldrich; girth ease against the Threads #221 p.71 *minimum ease* table). Three things about them are stated here because hiding any of them would be dishonest. First, `sewability_check` and the sourced point-valued half of `draft_math_check` are **ratchets**: the exit code is bound to a measured ceiling in `engine/tests/v5-ratchet-baseline.json`, not to zero, so "green" means "no worse than the day the ceiling was cut" and the standing violations still print on every run. Second, the girth-ease half of `draft_math_check` is deliberately **not** a ratchet — a published minimum cannot be ratcheted into a house ceiling, so those rows print `SERT HUKUM, ratchet DEGIL` and the gate's own closing line refuses to say `PASS`: it returns 0 only because closing them is a Damla decision on a body input (queued as `K-V5A`), and returns 1 the moment the violation count rises above the 2026-08-25 record. Run the gate for the wording; it prints which section, if any, drove the exit code. Third, the questions the shipped artefact cannot answer are printed as named ABSENTs rather than counted as passes — the `draftJSON` boundary carries no seam graph.

  ⚠ **The tail of that third point was true for one day and is corrected here rather than deleted.** It used to end "…so seam-pair length equality is not something this repo can currently assert at all". On 25 Aug 2026 one pair became assertable. Pattern pieces now carry edge ROLES — `armhole_front`, `armhole_back`, `sleeve_cap`, `sleeve_underarm` — given by the code that draws the edge and stored as an address (command range plus endpoint anchor), never as a length, so a consumer re-integrates the arc off the drawn geometry. That closed a tautology: the sleeve used to be found by a substring of the piece name, the cap by a hard-coded command index, and the armhole was not read off geometry at all but off a scalar the sleeve had already been solved against, so the reported agreement was one number agreeing with itself. `ctest -R sleeve_cap_ease_check` now measures the armhole arc against the cap arc, both off the SHIPPED bundle, against a published ceiling (Linda Lee, 1½ in) with the band's lower end printed as REPORTED because no publication was found that scales cap ease to the body. The honest half: where no piece carries an armhole role the validator still falls back to the old scalar, and the gate counts and NAMES those paths on every run instead of hiding them. Details: `docs/ARCHITECTURE.md` §15.
- **Editing has its own invariant, and the gate over it was measured toothless in one direction before it was tightened.** "Change the collar, leave everything else alone" is checkable: `ctest -R edit_locality_check` applies a spec diff, redraws through the *shipped* WASM bundle, and prints every panel outside the edited zone whose bytes moved. What makes it a gate rather than a formality is that it was attacked first — four deliberate breakages, three caught, and one *not*: relaxing the gate's own comparison from bytes to panel presence left it green, because its threshold was "caught at least one case of twelve". That direction is now closed by tightening, never by relaxing: the catch count is ratcheted to today's measured floor (and going above the floor without bumping it also fails), silently skipped cases are printed by name and capped, and the comparison's granularity is declared in `engine/tools/spec-diff.mjs` and then audited — the gate moves one coordinate on an untouched panel by 0.001 mm and requires the report to call it a violation. The limits are declared rather than glossed: one body, one base spec, and the zone law it reads is a hand-written document with no guard behind it.
- **Real-product benchmark — and the honest part is that it cannot be re-run here.** The producing tool is named rather than implied: `engine/tools/benchmark-58.mjs` runs every ground-truth photo through the live analyze chain and classifies each result FULL / MISSING / WRONG against `benchmark-58/manifest.json`. The tool is in the repo; **its input is not.** Checked on 25 Aug 2026: `benchmark-58/manifest.json` **does not exist** in this repo and neither does the `benchmark-58/` corpus around it — purchased/copyrighted, gitignored, never committed — and the run additionally needs paid live worker calls, so nobody can reproduce a score from a clean checkout. The standing pair this line used to headline — "27 of 54 under the strict counting method, 37/54 under the older, looser count" — is therefore a reading with no runnable provider behind it today, and it is recorded as that rather than restated as a fact. What the benchmark is *for* still holds: it is the outside reference, the score that only moves when the engine genuinely learns to draw something new, and the misses go in the patch notes. Restoring the corpus is what would make it a number again.

- **What the website says about the engine is now a test, not an editorial decision.** For weeks the pages sold made-to-measure and a EU34–52 run — a product this repo killed on evidence on 29 Jul 2026 and a size run `contract/layers/shape-ratios.json` does not publish. That is a class of failure a person re-reading their own copy does not catch, so it was given a gate: `ctest -R landing_truth_check` (`engine/tests/landing_truth_check.mjs`) parses every HTML file under `web/` and `web/js/*.js` into claim blocks — text nodes, translated attributes, JS string literals — and asks five questions of them: does a claim carrying a number also name a test or tool that actually exists in `engine/CMakeLists.txt` / `engine/tools`; does it use a banned promise or standing-claim pattern; is the vision section marked and written in future tense; does `site-health.mjs` come back clean; and is every `EU` size label on the site inside the published set, with the visitor's own picker list no wider than the engine's. The last one is why the size run is now mechanical: `web/js/create.js` derives its list from the contract instead of restating it. Recorded debt sits line by line in `engine/tests/landing-truth-baseline.json` and can only shrink. Its own limits are declared rather than glossed — it judges the FORM of a claim and never its truth, so a matched tool name is not evidence the number came from that tool. Seven patterns were escaping it; each one is now covered by a mutation the gate fires on.

**The honest limit:** this is a muslin-first pattern. The engine drafts to seven measurements and fills the rest (cup, arm girth, shoulder slope) from documented assumptions. The invariants above guarantee the draft is *buildable and reproducible*, not that it fits off the printer — sew a toile first. One reason is now measured rather than suspected: the engine's girth allowance is **multiplicative** (the hip allowance divided by the hip measurement is bit-constant at 0.2000 across all eight sizes) where every published ease band is **additive**, which puts the hip ease under Threads' published *minimum* in 8 of 8 sizes and the bust ease under it in EU34–EU40. Repairing it is an open decision, not a pending patch — and the first candidate has already been measured and **refuted**: shifting the body input was re-run on 25 Aug and would need the hip input at 254 cm to reach the published floor, because the allowance moves at only 0.0200 mm per mm of body (`ctest -R draft_math_check` is what prints it). That leaves the multiplicative constant inside `engine/src` as the only honest candidate, which by construction re-pins three golden references and puts eight currently-green gates back on the table. The taste/vein judgement of a pattern is still Damla's call, not a machine's.

## Tech

- **engine:** C++17, CMake, ctest. Single-file WASM bundle via emscripten/embind.
- **web:** static HTML/CSS/JS on GitHub Pages, no framework. Patterns are SVG; printing is client-side tiled A4 PDF. Measurements live in local storage — nothing about your body is uploaded, by architecture.
- **backend:** one Cloudflare Worker that proxies the vision model behind an app token and per-IP rate limits. The browser never holds an API key.
- **interchange:** DXF-AAMA/ASTM export, per-size graded DXF, machine-readable tech-pack manifest + PDF spec.

## Repo layout

- `engine/` — C++ kernel, tests, tools, WASM build (`src/dxf`, `src/nest`, `src/recipe`, `tools/tech-pack.cpp`)
