# stitchu architecture

How a garment photo becomes a printable, body-fitted sewing pattern. Companion doc: `engine/FORMULAS.md` (every drafting formula and its gotchas — the engine's spec); it was on disk when this line was checked on 2026-08-22. The two other companions this line used to name, `PROJECT.md` (roadmap) and `PLAN.md` (track A/B directives), are **not on disk** — the live roadmap/queue surfaces are `HEDEF.md` and `DAMLA-KUYRUK.md` at the repo root.

## The contract (`contract/`, K1 2026-07-19)

One versioned contract binds every layer boundary. `garment-spec.schema.json`: the SEMANTIC garment language (closed enums + bounded scalars) — the only language the vision model or a human speaks; the render layer is NOT in the contract, each renderer compiles its own parameters from the semantics, and the runtime gate (`web/js/spec-validate.js`, additionalProperties:false) strips any render knob smuggled into a vision answer. `tables.json`: every shared value (skirt lengths mm, EU size chart, gather ratios, flat drawing units, cross-layer word maps like sleeveHead→sleeveCap and the backDetail three-way split) — generated by `engine/tools/gen-contract.mjs` into `engine/src/contract.gen.hpp`, `web/js/contract.gen.js`, `backend/contract.gen.js`; consumers never copy numbers. `terms.json`: the term registry (id, canonical, synonyms, drawable|honest status, capability, evidence) — the benchmark counter's base since the DRAWN_SINCE regex list was retired. Guard: `engine/tools/validate-contract.mjs` runs as ctest `contract_check` and fails on any schema/vocab drift, registry defect, generated-file desync, 58-set unmapped phrase, undeclared flat recipe field, gate-fixture failure, or a create.js picker option outside the vocabulary.

## Layers

```
photo ──> Cloudflare Worker (Claude vision) ──> confirmed GarmentSpec
                                                      │
7 measurements (local) ───────────────────────────────┤
                                                      ▼
                        C++ engine (WASM, in-browser)
                        geometry core → blocks → garment drafter → validator
                                                      │
                                                      ▼
                        web app: SVG render → tiled A4 PDF print
```

### 1. Geometry core (`engine/src/geometry.*`)
Point/Path/cubic-Bezier primitives, seam-length measurement, outline offsetting, intersection and self-intersection checks. Everything above is built on these; they were unit-tested first (`tests/test_geometry.cpp`). Conventions (from `FORMULAS.md`): all geometry in millimeters, each piece in its own local space, curves flattened to 24 segments for length measurement (16 for self-intersection). Gotcha: `boundingBox()` counts curve control points, so comparisons must use flattened boxes.

### 2. Blocks (`bodice.cpp`, `skirt.cpp`, `sleeve.cpp`)
Parametric drafting blocks from published sources (FreeSewing Bella/Titan, Muller & Sohn, Aldrich), driven by 7 measurements plus percent ease (never fixed cm) — the numbers live in `engine/src/bodice.cpp` / `engine/src/skirt.cpp` / `engine/src/sleeve.cpp`, and the gate that redraws them is ctest `engine_check`. Documented assumptions — underbust = bust − 70 mm and shoulder drop ≈ 13° — are flagged in `FORMULAS.md`, live in `engine/src/bodice.cpp`, and are covered by the muslin warning in the sewing guide. If the two disagree, the file wins, not this page.

### 3. Garment drafter + manipulation layer (`garment.cpp`, `ruffle.cpp`, `keyhole.cpp`)
Combines blocks into garments (dress = bodice + skirt + CB invisible zipper; tops with hem variants) and applies the couture vocabulary: necklines (crew/scoop/v/square/boat/sweetheart), keyhole cut-out with shaped facing, halter (a frame-shift over the same bodice skeleton — no separate block), tiered ruffles (tier i edge = edge × fullness^(i−1)), pleats, gathers. Every vocabulary feature is an opt-in `GarmentSpec` field defaulting OFF; whether the base draft is unchanged to the byte without it is decided by ctest `golden_check` (green in the 2026-08-22 run, `GECE/log/F0v3.ctest.txt`).

### 4. Seam allowance / cut line (`geometry.cpp offsetOutline`)
The piece outline IS the sewing line; the cut line is a drawn outward offset. The outward side is found empirically (probe the longest edge's normal with point-in-polygon — traversal direction is not trusted, an area-sign heuristic once shipped an inward offset). Per-edge offset with miter/bevel joins, then an envelope guarantee: relax passes push any point closer than the allowance back out to exactly it (tames concave curves with radius < allowance, e.g. sleeve underarm). Fold edges are not seams: clamped, exempt from the audit. Strip pieces (ruffles, bias binding) stay single-line — their allowance lives in the cut note.

### 5. Validator (`validator.cpp`)
Geometric invariants run on every draft, and at runtime before any PDF: side-seam balance, dart sums, armhole/cap ease, waist joins, self-intersection, print fit, cut-line sanity. A broken pattern cannot reach the printer. Trim pieces (names containing "Ruffle") are excluded from structural sums by design.

### 6. Verification (tests, golden, fuzz, precision)
- `tests/engine_check.cpp`: the matrix — EU 34-52 + edge bodies × the full spec space = 70,200 drafts, all must validate. Per-feature checks (`ruffle_check`, `sweetheart_check`, `keyhole_check`, `halter_check`, `cutline_check`, ...) assert piece geometry, printability (≤3000 mm tile cap) and a base draft unchanged to the byte. How many suites there are is whatever `ctest --test-dir engine/build -N` prints — it listed **96** tests on 2026-08-22, and the run of that day recorded 89 passing / 7 red (`GECE/log/F0v3.ctest.txt`). (This line said "8 ctest suites" until 2026-08-22; that count was years of growth stale.)
- Golden: `engine/golden-reference.csv` (committed) is the pinned deterministic reference; `golden-diff.py` compares at 0.1 mm tolerance. History: the C++ engine was ported from Swift against a Swift golden dump (2805 drafts, port fidelity), then the golden was re-pinned to the C++ output when precision truing deliberately improved on the Swift geometry.
- `tools/precision-report.js` ("the tailor's micrometer"): measures every seam pair a sewist pins; the fail threshold is written in `engine/tools/precision-report.js`. It found and closed an 8-10 mm shoulder-pair gap and a ~2 mm empire side-seam gap, both measured by `engine/tools/precision-report.js` at the time. Run it after any bodice change — the number is the tool's, not this file's. Its 2026-08-22 run printed:

- `tools/web-fuzz.js`: fuzzes the WEB layer's spec mapping (what `create.js` actually sends to `draftJSON`) across body-corner measurements and simulates the print packer's math. ⚠ **RED on 2026-08-22**: `node engine/tools/web-fuzz.js` exited 1 with `web fuzz: 26260 drafts | 6513 validator-blocked (honest) | max 102 sheets | 3 FAILURES`. ### 7. WASM boundary (`engine/wasm/bindings.cpp`)
A thin embind layer exposing `draftJSON(measurements, spec) → JSON pieces`. Built by `engine/build-wasm.sh` into a single-file bundle (`engine/dist/stitchu-engine.js` — `ls -l` reported **1 128 760 bytes ≈ 1.1 MB** on 2026-08-22, 5.2× the "~218 KB" this line used to claim), copied to `web/vendor/`. The same file is `require()`-able from Node, which is how the fuzz/precision/proof tools drive the real engine — no parallel JS implementation to drift.

### 8. Web app (`web/`)
Static, framework-free. ⚠ Two publishers are declared at once (2026-08-22): `.github/workflows/pages.yml` and `web/vercel.json`, entry point `scripts/deploy.sh`; which one serves `stitchu.noseydewdrop.com` was **NOT measured (2026-08-22)**. `store.js` (measurements + closet, local), `analyze.js`/`create.js` (photo → Worker → confirm → draft), `render.js` (SVG pieces with darts, grainline, double cut/sew line), `print.js` (client-side tiled A4 PDF, 3 cm calibration square, 190×250 mm printable page, page map), `wall.js` (communal stitch wall via Worker KV). EN/TR i18n. Cache-busting is **no longer hand-maintained** (stale line replaced 2026-08-22): the `?v=N` stamp comes from one source, `engine/tools/site-version.mjs`, and a regression in it is caught by `node engine/tools/site-health.mjs`, whose 2026-08-22 run printed `checked: 127 pages, 2597 internal refs, 124 sitemap urls, 124 indexable pages` / `no dead links, sitemap matches the site, one version` (exit 0). Deploy goes through `scripts/deploy.sh` with `.github/workflows/pages.yml` + `web/vercel.json`, not the old `git subtree split --prefix web` → `gh-pages` route.

### 9. Backend (`backend/worker.js`)
One Cloudflare Worker: proxies garment analysis to Claude vision. The browser never holds the API key — it sends a shared app token; the key is a Worker secret. Rate-limited (20/min app-token; public mode 3/min, 15/day per IP), hardened per the 2026-07-13 ship-check. Also serves the stitch wall (KV). `POST /api/draft` — the sellable API, the same WASM engine run server-side — is **no longer "planned": it is written** (`backend/draft.js:1`, `backend/worker.js:70` for `/api/draft` and `:94` for `/api/grade`), and its wiring is covered by ctest `api_wire_check`, green in the 2026-08-22 run (`GECE/log/F0v3.ctest.txt`). Whether the deployed endpoint answers a real request was **NOT measured (2026-08-22)** — no request was sent to the live host.

## Data flow summary

- Measurements: entered once, IndexedDB/local only, never leave the device for drafting.
- Photo: leaves the device only for the vision call (Worker → Anthropic), user confirms the classification before drafting.
- Drafting: 100% client-side (WASM) — zero server cost per draft, and simultaneously the KVKK/privacy answer. That the browser bundle draws the same numbers as the native engine is decided by ctest `recipe_wasm_parity` and `dxf_wasm_parity`.
- Pattern: SVG + PDF generated in the browser; saved patterns live in the local closet (full CRUD).
- Knowledge: `knowledge/schema.sql` + seeds → `stitchu.db`; formula claims enter as `verified` only after adversarial source-checking, refuted claims kept so they are never reused.

## Key design decisions

- C++ core, multiple consumers: one engine feeds web (WASM), Node tooling (same bundle), later iOS (static lib) and Android (NDK). Chosen over Rust deliberately (synergy with coursework); the golden matrix is what made a full Swift→C++ rewrite safe.
- Client-side drafting: no server cost, no measurement upload, shareable static hosting.
- Spec-driven port: `FORMULAS.md` is the source of truth, not line-by-line translation — the port implements the spec.
- Opt-in vocabulary: every new feature defaults off, and the gates that decide whether it stayed that way are ctest `engine_check` (the matrix) and `golden_check` (base draft unchanged to the byte). A feature that turns either red is reverted, not shipped.
- Prove, don't claim: a feature exists only when it is in `engine/src`, has a passing `_check` test, renders correctly, and survives the matrix + golden + precision + fuzz loop. (That discipline used to be attributed to `PLAN.md`; the file is gone — the written form on disk today is `RULES.md`, "Per-feature discipline", 7 steps.)
- One truth, one place: neck width, armhole curve, binding length each have a single computing site; derived values are measured from the same geometry, never recomputed.
