## 0. İKİ ALET TUZAĞI — ÖLÇÜLDÜ, KARTIN ÖNERDİĞİ DÜZ CLI YETMEDİ

Kart `--headless=new --screenshot --window-size=320,640` öneriyordu. Denendi,
**iki yerde yalan söylüyor** — ikisi de sayıyla:

1. **`--window-size=320,640` viewport'u 320'ye İNDİRMİYOR.** Aynı probe düz CLI
   ile koşulduğunda `document.documentElement.clientWidth` = **500** döndü
   (bu makinede headless pencere tabanı 500 CSS px). Yani düz CLI ile 320px
   reflow ölçümü **yapılamaz** — 320 sanıp 500 ölçersiniz.
   → Çözüm: Chrome `--remote-debugging-port` ile açıldı,
   `Emulation.setDeviceMetricsOverride {width:320}` ile viewport **tam 320**'ye
   zorlandı. Doğrulama: raporun her satırında `"viewport": 320` yazıyor.
2. **`--headless=new` iş bitince süreci KAPATMIYOR.** `--screenshot` /
   `--dump-dom` çıktıyı üretiyor ama process asılı kalıyor
   (`ps aux | grep "[C]hrome --headless"` → 4 zombi süreç sayıldı, 12:38–13:02).
   Bu yüzden ilk 9'lu döngü tek PNG'de kilitlendi. CDP yolunda süreç
   `Browser.close` + `SIGKILL` ile kapatılıyor.

**ÜÇÜNCÜ TUZAK — `file://` SAYFAYI BOŞ GÖSTERİYOR.** `web/create.html`'in
gövdesini `<script type="module" src="js/create.js">` basıyor; ES module
`file://` altında CORS ile bloklanır. `file://` ile ölçüldüğünde create.html
`pageHeight` = **640** (= viewport, yani BOŞ) ve DOM'da 0 ekran öğesi vardı.
HTTP üzerinden aynı sayfa `pageHeight` = **4692**. `file://` ile alınan ilk üç
create PNG'si **silindi**; aşağıdaki 9 PNG'nin hepsi HTTP'den.

Statik sunucu: `python3 -m http.server 8123 --directory web` (yeni bağımlılık
değil, Python stdlib).

## 3. TAŞMA TABLOSU — ÖNCE

Ölçüm `body{overflow-x:hidden}`'a GÜVENMEZ. `web/index.html:34`'te gerçekten
`body{...overflow-x:hidden...}` var; probe taşmayı clipleyen bütün
`overflow:hidden|clip` atalarını geçici olarak `visible` yapıp
`documentElement.scrollWidth`'i **ikinci kez** okuyor
(`scrollWidth_clipped` vs `scrollWidth_unclipped`). İkisi eşitse örtülen taşma yoktur.

| sayfa | genişlik | viewport | scrollWidth (clipped) | scrollWidth (hidden'lar AÇIK) | viewport'u aşan öğe |
|---|---|---|---|---|---|
| index  | 320 | 320 | 320 | **320** | 0 |
| create | 320 | 320 | 320 | **320** | 0 |
| api    | 320 | 320 | 320 | **320** | 5 (hepsi `pre` içinde, aşağıda) |
| index  | 390 | 390 | 390 | **390** | 0 |
| create | 390 | 390 | 390 | **390** | 0 |
| api    | 390 | 390 | 390 | **390** | 4 (aynı `pre`'ler) |
| index  | 1440 | 1440 | 1440 | **1440** | 0 |
| create | 1440 | 1440 | 1440 | **1440** | 0 |
| api    | 1440 | 1440 | 1440 | **1440** | 0 |

**HÜKÜM: 320 px'te SAYFA DÜZEYİNDE YATAY KAYDIRMA YOK — üç sayfanın üçünde de.**
`index.html`'in `overflow-x:hidden`'ı bir şeyi ÖRTMÜYOR: açıldığında sayı
kımıldamıyor (320 → 320). Kart "yalnız o kırılımı onar" diyordu; onarılacak
sayfa-düzeyi kırılım **çıkmadı**, bu yüzden `web/**` altında **tek bayt
değiştirilmedi** ve "sonra" sütunu "önce" ile aynıdır.

### api.html'in 5 öğesi — nedir, neden onarılmadı

Beşi de `web/api.html`'in iki kod bloğunun (`pre`) içindeki `<span class="s">` /
`<span class="k">`. `pre` kuralı `web/api.html:39`: `overflow:auto`.

| 320 px'te öğe | genişlik | viewport'u aşma |
|---|---|---|
| `span.s` (curl gövdesi) | 639.69 px | +368.69 px |
| `span.k` | 60.22 px | +316.05 px |
| `span.k` | 90.31 px | +165.52 px |
| `span.k` | 120.42 px | +142.95 px |
| `span.s` | 240.83 px | +7.47 px |

İç kaydırıcılar (`overflow-x:auto` + `scrollWidth > clientWidth`), 320 px'te:
`pre` **680 px içerik / 262 px kutu**, `pre` **755 px / 262 px**.

Bunlar kutunun İÇİNDE kayıyor, sayfayı kaydırmıyor (`scrollWidth_clipped` = 320).
WCAG 2.2 SC 1.4.10 iki boyutlu yerleşim gerektiren içeriği istisna tutuyor ve
kod örneği bu istisnaya girer. **DOKUNULMADI** — kart "yalnız kırılımı onar,
redesign yapma" diyor, sayfa kırılmıyor. Karar Damla'nın: `curl` örneğini
telefonda sarmalı mı (`white-space:pre-wrap`) yoksa kaydırmalı mı kalsın?
